# System resilience hardening: webhooks, email deliverability, connection management, and data consistency

This change addresses ten classes of production reliability issues across NuCRM's webhook retry system, email deliverability pipeline, database/Redis connection management, form builder safety, lead scoring concurrency, contract lifecycle, cursor pagination, batch job recovery, and drag-to-reorder consistency. The approach is defensive: circuit breakers and fallbacks for infrastructure failures, distributed locks for concurrent access, input sanitization at storage boundaries, and validation for state machine transitions.

Watch for: the bulk email batch job recovery is incomplete — the "batch record" tracking is mentioned in the feature spec but only the DNC filter and try-catch wrapper shipped, meaning a crash mid-loop still causes duplicate sends (confirmed). The `acquireLock` fallback when Redis is unavailable returns `{ acquired: true }`, which means distributed locks provide no protection in memory-only deployments (confirmed). The lead scoring `SELECT FOR UPDATE` targets `contact_scores` but the first scoring for a contact has no row to lock — the INSERT's unique constraint serializes that case, but a concurrent read-then-write on the `contacts.score` column is still unguarded (likely).

**Verdict**: NEEDS_CHANGES

## High-level view

The webhook retry system gains concurrency limiting (batches of 5), a corrected retry delay array that now has 5 entries matching `MAX_RETRIES=5`, initial failure correctly sets `attempt=1`, and the DLQ purge is wired into the cron. The backoff cap is added in `delivery.ts` but not in the main `webhooks.ts` retry path (which uses the delay array directly — that array is already capped by design). The design is sound, though `retryWebhookItem` has a double dead-letter condition (`retryDelay < 0 || nextAttempt >= MAX_RETRIES`) where both branches can fire on the same attempt, which is harmless but semantically redundant.

Email deliverability adds RFC 8058 List-Unsubscribe headers via an HMAC-signed URL, hard/soft bounce differentiation with a 3-within-7-days escalation policy, warmup bounce-rate monitoring that auto-pauses above 5%, and DNC filtering in both bulk email endpoints. The unsubscribe HMAC falls back to a hardcoded secret (`nucrm-unsub-default`) when neither `UNSUBSCRIBE_SECRET` nor `NEXTAUTH_SECRET` is set, which undermines the tamper protection.

Connection pool exhaustion detection rejects new requests when more than 50 clients are waiting, and `safeTransaction` now passes `true` to `client.release()` on error so pg destroys broken connections rather than recycling them. The Redis cache adds a circuit breaker (3 failures opens it for 60s) and a periodic reconnection timer. The reconnect timer creates a new client by nulling the singleton and setting `redisPermanentlyDisconnected = false`, relying on the next `getRedisClient()` call to instantiate it — this is clean but the timer's `setInterval` never clears itself on successful reconnect from within the timer callback (it checks `redisPermanentlyDisconnected` at the top, but that flag is only cleared externally by the `connect` event handler racing with the interval).

The form builder sanitizes stored submissions with HTML entity encoding and rejects duplicate field IDs via a Zod refine. The contract lifecycle removes a self-join filter bug (`eq(contracts.tenantId, contracts.tenantId)`) in the renewal cron and adds status transition validation. The pipeline reorder wraps stage updates in a `SELECT FOR UPDATE` on the pipeline row. The sequence processor acquires a distributed lock before processing enrollments.

The batch email endpoint filters out DNC contacts and wraps the send loop in try-catch to return partial results on crash, but does not track per-contact send progress — a restart re-queries contacts and re-sends to all that pass the filter, because there is no "already sent in this batch" marker.

<details>
<summary>Issues (8)</summary>

1. **Bulk email duplicate sends on crash** — The batch job recovery feature spec says to track per-contact completion, but the implementation only adds DNC filtering and a try-catch. A server restart mid-loop will re-send to contacts that already received the email. Add a batch job record with per-contact completion tracking.
2. **Unsubscribe HMAC hardcoded fallback secret** — `buildUnsubscribeHeaders` uses `'nucrm-unsub-default'` when env vars are missing, making unsubscribe tokens guessable in misconfigured deployments. Throw or log a critical warning instead of falling back silently.
3. **Distributed lock no-op without Redis** — `acquireLock` returns `{ acquired: true }` when Redis is unavailable, making sequence processor and pipeline reorder locks meaningless in single-Redis-failure or development scenarios. Document this or add a DB-based fallback for critical locks.
4. **Lead scoring concurrent contact.score write** — `SELECT FOR UPDATE` on `contact_scores` serializes score persistence, but the subsequent `UPDATE contacts SET score=...` in the same transaction doesn't lock the contacts row. A concurrent non-scoring update to the same contact could read a stale score. Use `FOR UPDATE` on the contacts row too, or accept eventual consistency.
5. **Redis reconnect timer never self-clears** — `startReconnectTimer` checks `redisPermanentlyDisconnected` to bail early, but the `connect` event handler (which clears that flag) fires on the _new_ client created by the timer, after the timer already returned. There's a narrow window where the interval fires again, creates a second client, and the first one is orphaned. Add explicit `clearInterval` in the `connect` handler.
6. **Form XSS sanitization bypasses nested objects** — `sanitizeFormData` handles strings and arrays of strings, but does not recurse into nested objects. A field value like `{ "nested": "<script>..." }` passes through unsanitized. Either recurse fully or reject non-primitive field values at the schema level.
7. **Contract status transition allows no return from 'expired'/'terminated'/'cancelled'** — The `VALID_TRANSITIONS` map has no entries for `expired`, `terminated`, or `cancelled`, meaning the `allowed` lookup returns `undefined` and the guard is skipped (`if (allowed && ...`). A contract in these terminal states can be moved to any status. Add explicit empty arrays for terminal states.
8. **Warmup bounce rate uses totalBounced across all time** — The bounce rate calculation divides all-time bounces by all-time sends, which means a config that sent 10,000 emails with 400 early bounces (4%) will never recover even if recent sends are clean. Consider a rolling window (e.g., last 7 days) for the bounce rate check.

## Bulk email batch job recovery gap

The feature spec (FEAT-003 step 11) describes inserting a batch job record with total/completed counts and skipping already-processed contacts on retry. The actual implementation in `app/api/tenant/email/bulk/route.ts` adds only two things: a DNC filter in the WHERE clause and a try-catch around the loop that returns partial results. There is no persistent record of which contacts received the email in this batch invocation.

If the server process dies between sending email #20 and #21, the next request (manual retry or automated) will re-query the same contact list, and since `sendEmail` has no idempotency key, contacts 1-20 receive the email twice. The DNC filter doesn't help here because these contacts aren't DNC — they successfully received mail.

The fix is straightforward: create a batch record before the loop, mark each contact as processed after successful send (or use a set of sent IDs stored in the batch metadata), and skip already-sent contacts on re-entry.

## Unsubscribe header HMAC secret fallback

In `lib/email/service.ts`:

```typescript
const secret =
  process.env.UNSUBSCRIBE_SECRET ||
  process.env.NEXTAUTH_SECRET ||
  "nucrm-unsub-default";
```

The chain falls through to a publicly-known constant. Any attacker who reads this source (or guesses a common pattern) can forge unsubscribe tokens for arbitrary contact IDs by computing `HMAC-SHA256('nucrm-unsub-default', contactId)`. In production this means contacts can be unsubscribed by anyone who knows (or brute-forces) their contact UUID.

This should either throw when no secret is configured (preventing accidental production deployment without the var) or at minimum emit a startup warning that unsubscribe tokens are insecure.

## Distributed locks degrade to no-op on Redis failure

`acquireLock` in `lib/cache/index.ts`:

```typescript
if (!redis || redis.status !== "ready") return { acquired: true, value: "" };
```

When Redis is down (or the circuit breaker is open), every caller believes it holds the lock. The sequence processor's distributed lock (`SEQUENCE_LOCK_KEY`) and the pipeline reorder lock both become no-ops, allowing concurrent cron runs and concurrent PATCH requests to proceed in parallel — exactly the scenarios the locks were added to prevent.

This is a deliberate "fail-open" design to avoid blocking all operations when Redis is unavailable, but for safety-critical locks (sequence deduplication), a "fail-closed" approach (return `acquired: false`) or a database-advisory-lock fallback would prevent duplicate sends.

## Lead scoring FOR UPDATE scope

The new code in `lib/ai/scoring.ts`:

```typescript
await tx.execute(
  sql`SELECT 1 FROM contact_scores WHERE contact_id = ${contactId} FOR UPDATE`,
);
```

This locks the `contact_scores` row, serializing concurrent `scoreLead` calls for the same contact. However, the transaction also writes to the `contacts` table (`SET score = finalScore`) without locking that row. If another transaction (e.g., a bulk update or manual score override) writes to `contacts.score` concurrently, one write is lost. The practical impact is low since AI scoring is infrequent and the `contacts.score` column is just a denormalized cache, but the inconsistency window exists.

Additionally, the `try { ... } catch {}` around the `SELECT FOR UPDATE` means that if the `contact_scores` row doesn't exist yet (first scoring), the lock is silently skipped and both concurrent calls proceed to `INSERT ... ON CONFLICT DO UPDATE`, which pg serializes correctly. So the first-score case is safe, but only because of the upsert semantics — the FOR UPDATE adds nothing in that path.

## Redis reconnect timer lifecycle

In `lib/cache/index.ts`, `startReconnectTimer` sets an interval that:

1. Checks if `redisPermanentlyDisconnected` is still true
2. Destroys the old client and sets `redis = null`
3. Clears `redisPermanentlyDisconnected`

The `connect` event handler on the _new_ Redis client (created by the next `getRedisClient()` call) sets `redisPermanentlyDisconnected = false` and calls `recordRedisSuccess()`. But the timer itself only clears when the _next_ interval tick finds `redisPermanentlyDisconnected === false`. Between the timer clearing the flag (step 3) and the new client connecting, there's a window where the timer has already returned but the flag is false, so the next tick bails early and the timer clears itself. This works in the happy path.

The race is: if the new client fails to connect (Redis is still down), `retryStrategy` fires again, sets `redisPermanentlyDisconnected = true`, and calls `startReconnectTimer()` which is a no-op (timer already exists). The next interval tick sees `redisPermanentlyDisconnected = true` and tries again. This is correct but wasteful — it creates and destroys Redis clients every 30s while Redis is down, each of which emits error events. Not a bug, but the error log noise could mask real issues.

## Form XSS sanitization depth

`sanitizeFormData` in `app/api/forms/submit/route.ts`:

```typescript
function sanitizeFormData(
  data: Record<string, unknown>,
): Record<string, unknown> {
  for (const [key, value] of Object.entries(data)) {
    if (typeof value === "string") {
      sanitized[key] = escapeHtmlEntities(value);
    } else if (Array.isArray(value)) {
      sanitized[key] = value.map((item) =>
        typeof item === "string" ? escapeHtmlEntities(item) : item,
      );
    } else {
      sanitized[key] = value; // Objects pass through unsanitized
    }
  }
}
```

The form submission schema accepts `z.record(z.string(), z.unknown())` for both `data` and `values`, meaning nested objects are valid input. A payload like `{ "notes": { "html": "<script>alert(1)</script>" } }` stores the script tag verbatim. Whether this is exploitable depends on how the frontend renders custom form data — if it uses `dangerouslySetInnerHTML` or an equivalent on deeply-nested values, the XSS fires.

The simplest fix: either reject non-primitive values in the schema (add a refine that walks all values and rejects objects) or recurse in the sanitizer.

## Contract status transition validation gap

In `app/api/tenant/contracts/[id]/route.ts`:

```typescript
const VALID_TRANSITIONS: Record<string, string[]> = {
  draft: ['active', 'cancelled'],
  active: ['suspended', 'terminated', 'expired', 'renewed'],
  suspended: ['active', 'terminated'],
  renewed: ['active'],
};

const allowed = VALID_TRANSITIONS[existing.status as string];
if (allowed && !allowed.includes(allowedFields.status)) {
  return ... 400
}
```

Terminal states (`expired`, `terminated`, `cancelled`) have no entry in `VALID_TRANSITIONS`, so `allowed` is `undefined`, the guard is skipped, and the transition proceeds unchecked. A contract that has been terminated can be moved back to `active` or `draft` via a PUT request. Adding `expired: [], terminated: [], cancelled: []` to the map closes this.

## Warmup bounce rate window

`processWarmUp` calculates bounce rate as:

```typescript
const bounceRate = calculateBounceRate(totalBounced, config.totalSent || 0);
```

Both `totalBounced` and `totalSent` are all-time counters. A config that had early deliverability problems (e.g., sending to a purchased list) but later achieved clean sending will carry the early bounce rate forever. Once `totalSent` is large enough to dilute the early bounces below 5%, the config stays active — but it can never recover from a brief spike that pushes it over 5% because the denominator grows slowly relative to the numerator freezing at the spike level.

A rolling window (bounces in last 7 days / sends in last 7 days) would be more operationally useful and would match the soft-bounce window logic already used in the Resend webhook handler.
