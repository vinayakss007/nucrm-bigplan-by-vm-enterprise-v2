# Critical bug-fix sweep v2: auth cookies, search injection, API normalization, onboarding dedup, reliability

This second pass re-examines the full change set (b165cc43..HEAD) after the six issues from the v1 review were addressed. The six v1 fixes are all confirmed resolved: frontend pages read `data.data`, products uses `escapeLike`, subscriptions count uses the full conditions array, the JSDoc is updated, and unique-violation detection checks error code `23505`. Three new concerns emerge from deeper analysis of the change set.

Watch for: The `escapeLike` utility does not escape backslash, which is the LIKE escape character in PostgreSQL — a user-supplied `\%` bypasses the protection and re-introduces a wildcard (confirmed). The onboarding pipeline deletion will throw a foreign key violation if any deals already reference the old pipeline's stages, because `deals.stageId` has no `ON DELETE` cascade (confirmed). The deals endpoint still caches responses keyed by raw `searchParams.toString()`, leaving the same cache-pollution vector that was removed from contacts (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The `escapeLike` utility neutralizes `%` and `_` but ignores `\`, which PostgreSQL uses as the default LIKE escape character. An input like `\%` passes through as `\\%`, which PostgreSQL interprets as a literal backslash followed by a wildcard percent — exactly the pattern the utility was meant to prevent. The fix is to escape `\` to `\\` before escaping the other two characters.

The onboarding route deletes existing default pipelines and their stages in a transaction, but `deals.stageId` references `deal_stages.id` without an `ON DELETE` clause (defaulting to `RESTRICT`). If a tenant created deals before running onboarding — possible if they skipped the wizard initially — the DELETE will fail with a foreign key violation, leaving the onboarding transaction rolled back and the user stuck.

The deals GET endpoint caches responses keyed by `searchParams.toString()`. Since URL parameter order is not normalized and extraneous params are not stripped, an attacker (or a buggy client) can fill the cache with entries that will never be hit on subsequent natural requests, wasting memory. This is the same pattern that was deliberately removed from the contacts endpoint in this PR.

## escapeLike backslash bypass

PostgreSQL's LIKE operator uses `\` as the default escape character. The `escapeLike` utility in `lib/api/sanitize-like.ts` escapes `%` → `\%` and `_` → `\_` but leaves `\` untouched:

```typescript
export function escapeLike(value: string): string {
  return value.replace(/%/g, "\\%").replace(/_/g, "\\_");
}
```

When a user searches for the literal string `\%` (two characters: backslash, percent), the function processes it as:

1. The `%` is found and replaced with `\%`, producing the three-character string `\` `\` `%`
2. PostgreSQL parses `\\%` in LIKE as: escaped backslash (literal `\`) + wildcard `%`

The result is that `\%` in user input restores the wildcard behavior. The fix:

```typescript
export function escapeLike(value: string): string {
  return value
    .replace(/\\/g, "\\\\") // escape backslash first
    .replace(/%/g, "\\%")
    .replace(/_/g, "\\_");
}
```

This affects all 10+ endpoints using `escapeLike`, since they all share the same utility.

## Onboarding pipeline deletion fails when deals exist

The onboarding POST deletes existing default pipelines and their stages:

```typescript
for (const old of existingDefaults) {
  await tx
    .delete(dealStages)
    .where(
      and(
        eq(dealStages.tenantId, ctx.tenantId),
        eq(dealStages.pipelineId, old.id),
      ),
    );
  await tx.delete(pipelines).where(eq(pipelines.id, old.id));
}
```

The schema defines `deals.stageId` as:

```typescript
stageId: uuid('stage_id').notNull().references(() => dealStages.id),
```

No `onDelete` cascade or set-null is specified, so PostgreSQL defaults to `RESTRICT`. If the tenant created any deals using the signup-created pipeline stages before completing onboarding, the `DELETE FROM deal_stages` statement throws a foreign key violation and rolls back the entire transaction.

The probability depends on whether users can create deals before onboarding completes. Since the onboarding step is the provisioning wizard (separate from the signup flow), and the app's nav is accessible after signup, there's no guard preventing deal creation before onboarding runs.

A safe approach: before deleting stages, reassign any deals that reference them to a new stage in the replacement pipeline (matching by stage name or falling back to the first stage), or update the existing pipeline in place instead of delete-and-recreate.

## Deals endpoint cache key pollution

The deals route constructs its cache key from raw search params:

```typescript
const cacheKey = `tenant:${ctx.tenantId}:deals:${searchParams.toString()}`;
const cached = await cache.get(cacheKey);
if (cached) return NextResponse.json(cached);
```

`searchParams.toString()` preserves parameter order and includes unrecognized parameters. A client appending `&_=<random>` to each request generates a unique cache key every time, filling the cache with entries that will never be read again. The contacts endpoint had the same pattern and this PR removed it entirely. The deals endpoint should receive the same treatment — either remove the cache or build the key from validated/normalized parameters only.
