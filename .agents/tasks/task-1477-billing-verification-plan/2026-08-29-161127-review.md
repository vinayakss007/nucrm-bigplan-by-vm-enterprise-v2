## Stripe status matrix and terminal guard (#1463)

Section 3 mirrors the `switch` in `handleSubscriptionUpdated` line for line: `active`/`trialing` to `active`, `past_due` to `past_due`, `canceled`/`unpaid`/`incomplete_expired` to `cancelled`, `incomplete`/`paused` to `past_due`, `default` fail-safe to `past_due`. The terminal-status guard row matches: `terminalStatuses = {suspended, deleted, cancelled}`, and when the existing status is terminal and the incoming mapped status is `active`, only `plan_id` is updated and the row returns without re-activating. The idempotency key (`stripe:evt:{event.id}`, 24h) and checkout activation path (`plan_id` fallback to `starter`, `billing_type='stripe'`, `status='active'`, requires `metadata.tenant_id`) also match.

## Cancellation status divergence (Stripe vs Razorpay)

The plan's most important reviewer-facing callout is that the two providers set a different `tenants.status` on cancellation. Verified: `handleSubscriptionDeleted` sets `plan_id='free'`, `status='active'`, `stripe_subscription_id=null`, `billing_type='trial'`; `handleSubscriptionCancelled` (Razorpay) sets `plan_id='free'`, `status='cancelled'`, `subscription_id=null`, `billing_type='trial'`, and writes `metadata.cancelled_at`. The plan documents each provider's expected status separately, which is correct given the asymmetry.

## Razorpay fail-open on handler error

The plan warns that the Razorpay handler returns HTTP 200 even when an inner handler throws (to stop Razorpay retries), unlike Stripe which returns 500 to force a retry, so a 200 does not by itself prove the side effect landed. This matches the `catch` block returning `{ received: true }`. The idempotency key derivation (`x-razorpay-event-id`, falling back to payment entity id, then subscription entity id; `razorpay:evt:{id}`, 24h) and `normalizeRazorpayPlan` (growth to pro, scale to enterprise, empty to starter, passthrough otherwise) are accurate.

## PayU hash, txnid, and per-txnid idempotency

Section 5 matches `app/api/webhooks/payu/route.ts`: reverse SHA-512 hash via `verifyPayUResponse` with a timing-safe compare; `txnid` format `NUCRM_{quoteId}_{random}` with the quote id validated as a UUID; a bad hash returns HTTP 400 `Hash verification failed`; an unrecognized txnid returns HTTP 200 with `processed:false, reason:'unrecognized_txnid_format'`. Idempotency is per-txnid inside one transaction with the latest live invoice locked `FOR UPDATE`; a duplicate `reference == txnid` (or an already-`paid` invoice) returns `alreadyProcessed:true` and inserts no second ledger row; terminal quote statuses (`accepted`/`declined`/`expired`/`cancelled`) are never re-flipped to `accepted`; failures are recorded on `quotes.metadata.payu.failures`, deduped by txnid and capped to the last 10.

## Invoice numbering concurrency and after-soft-delete (#1462)

Section 7 matches `app/api/tenant/invoices/route.ts`: generation inside a transaction holding `SELECT id FROM tenants WHERE id = ... FOR UPDATE`, next sequence from `MAX(regex-extracted suffix)+1`, `MAX_RETRIES=3` on `23505`, format `INV-#####` via `padStart(5, '0')`. The gap-safety reasoning is verified against `app/api/tenant/invoices/[id]/route.ts`: `DELETE` is a soft delete (sets `deletedAt`, `deletedBy`, `status='cancelled'`), the soft-deleted row still counts toward `MAX(sequence)`, so its number is never reused. The unique index `idx_invoices_number` on `(tenant_id, invoice_number)` matches `drizzle/schema/billing.ts`.

## Dunning cap and attemptNumber (#1464)

Section 8 matches `app/api/tenant/billing/dunning/retry/route.ts`: admin-only and requires `isStripeConfigured`; `maxRetries` from `dunning_settings.max_retries` (default 3); cap counts `dunning_attempts` where `status != 'succeeded'`; `attemptNumber = MAX(attempt_number)+1` across all attempts; the subscription row is locked `FOR UPDATE`; hitting the cap throws `DunningCapReached` and returns HTTP 400 containing `Maximum retry attempts`. The plan's caveat that the route only records the attempt plus a `billing_events` row and does not yet re-charge Stripe (explicit TODO) is verified, and it correctly scopes the dunning test to bookkeeping and cap enforcement rather than a successful charge.

## Currency and integer minor units

`lib/money.ts` (`money`, `round2`, `lineTotal`, `sumLineItems`, `documentTotal`) rounds to cents at each accumulation step, and `lib/billing/payments.ts` uses `toCents` (`Math.round(value * 100) / 100`) when deriving the summary from the ledger. `RAZORPAY_PLAN_PRICING.starter.month = 149900` paise = 1,499 INR matches `lib/razorpay.ts`. The plan's currency-consistency risk is real: `billing_events.currency` defaults to `'usd'` and is hard-coded `'usd'` in the upgrade and dunning-retry inserts, and `service_subscriptions.currency` defaults to `'USD'`, even though Razorpay pricing is INR. Correctly flagged as report-only.

## Proration section (#10)

The upgrade route exists at `app/api/tenant/billing/subscription/upgrade/route.ts` and matches the plan: admin-only, requires `isStripeConfigured`, proxies proration via `updateSubscription`, updates `subscriptions` (`plan_id`, `status='active'`, `current_period_start/end` from the Stripe sub), writes a `subscription.upgraded` billing event, and returns HTTP 400 `This is not an upgrade. Use downgrade endpoint instead.` when the target `priceMonthly` is not greater than the current plan's. The one caveat is that proration math can only be checked against the Stripe dashboard, so step 2 has no DB-only pass/fail; the plan says as much.
