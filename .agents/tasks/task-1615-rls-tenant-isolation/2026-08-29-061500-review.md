# Full-handler connection pinning via withApiRoute (v2)

This pass adds `withApiRoute()` (and a Server-Component sibling `withTenantScope()`) in `lib/api/with-api-route.ts`, which encloses an entire Next.js route handler body — auth plus every subsequent `db` query — in a single `withPinnedConnection` scope. This directly answers the v1 blocking finding: v1 pinned only inside `requireAuth()`/`requireTenantCtx()`, whose AsyncLocalStorage scopes close before handler queries run, leaving the exact surface #1615 is about (handler queries with a missing `tenant_id` filter) on unpinned pool connections. The wrapper's nested `withPinnedConnection` inside `requireAuth` reuses the already-pinned client rather than acquiring a second connection, and four representative routes (`admin/flags`, `tenant/contacts`, `tenant/contacts/[id]`, `tenant/deals`) are converted. A new DB-free unit test drives the real wrapper and proves a client is pinned at the point the handler runs its later query.

Watch for: the mechanism is now correct and proven, but only 4 of 485 route files (and 0 of the many `requireTenantCtx`-based Server Component pages, despite `withTenantScope` being available) are converted — so ~386 auth'd routes plus every server-rendered page still run handler queries unpinned and RLS-inert, which is the residual that decides whether #1615 can close (**confirmed**). The wrapper itself has no leak/double-release hazard (**confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

The wrapper is the right shape and resolves the v1 blocking concern at the primitive level. `withApiRoute(handler)` runs the original body inside `withPinnedConnection`, so `requireAuth`'s `setTenantContext()` and the handler's later `db` queries share one pinned connection and the session-scoped tenant GUC is visible to every query. The nested `withPinnedConnection` in `requireAuth` short-circuits on the existing pin (runs `fn()` without acquiring or releasing), so there is exactly one `connect()`/`release()` per request and no double-release. Response returns, route params, and thrown errors pass through unchanged.

The gap that remains is coverage, not correctness. Four route files are converted; the repo has 485 route files, ~390 of which run auth + their own queries. The other ~386 still exhibit precisely the v1 defect: their handler queries run outside any pin, on empty-GUC pool connections, protected only by app-level `tenant_id` filters. `withTenantScope` is exported for Server Components but wired into zero pages, so the server-rendered read surface (contacts, deals, dashboard, companies pages) is entirely unpinned. #1615 is a CRITICAL cross-tenant-isolation defect whose acceptance criterion is that RLS blocks a filter-less cross-tenant read in a real request path; that now holds for 4 routes and no page, so the vulnerability the issue describes remains live across the large majority of the tenant-data surface.

The v1 test gap is addressed. The new DB-free `with-api-route.test.ts` uses the real `withPinnedConnection` (mocking only `pool.connect`) and asserts a client is pinned when the wrapped handler runs its later query — the fail-without/pass-with proof v1 lacked — plus release+reset-once, params/request passthrough, error propagation, and the PgBouncer no-op. The live-DB integration test adds a `withApiRoute`-wrapped, filter-less handler that self-skips without Postgres. v1 issues #3 (pool re-resets unconditionally on the non-PgBouncer release path) and #4 (client-logger eslint-disable removal, incidental) are resolved/accepted.

### withApiRoute encloses the whole body; nested reuse avoids a second acquire

`withApiRoute(handler)` returns `(request, context) => withPinnedConnection(async () => handler(request, context))`. The wrapper acquires and pins one client, runs the handler inside the ALS scope, and the primitive's `finally` resets GUCs and releases once. When the handler calls `requireAuth`, that helper's own `withPinnedConnection` hits the `existing = getPinnedClient()` branch and returns `fn()` directly — no second `connect()`, no `release()`, no early GUC reset. So the outer wrapper owns the single acquire/release and the handler's post-auth `db` queries resolve through the proxy to the same pinned client that `setTenantContext()` wrote the GUC on. This is the fix v1 asked for, and the reuse path closes the double-acquire/leak hazard the briefing flagged.

```
withApiRoute(GET)
  └─ withPinnedConnection            ← acquires client C, enters ALS scope
       └─ handler(request)
            ├─ requireAuth(request)
            │    └─ withPinnedConnection  ← existing pin found → runs fn() on C, no acquire/release
            │         └─ setTenantContext() → sets tenant GUC on C
            └─ db.select(...)             ← resolves to C (pinned) → GUC visible → RLS enforced
       finally: reset GUCs on C; C.release()   ← exactly once
```

Thrown handler errors — and Next.js `redirect()`/`notFound()` control-flow throws on the `withTenantScope` path — unwind through the `finally` (client released, GUCs reset) and re-propagate unchanged, so wrapping does not swallow or alter framework control flow. Params passthrough is a plain forward of the second argument via the generic `C`, so dynamic routes keep their `{ params: Promise<...> }` type.

### The residual is the deciding question, and it is not sufficient to close #1615

v1's blocking finding was that the pin didn't reach handler queries. v2 builds the correct tool to reach them but applies it to 4 of 485 route files. The unconverted ~386 auth'd routes are byte-for-byte in the v1-defective state: `const ctx = await requireAuth(request)` (pin acquired and released inside the helper), then handler `db` queries on a fresh pool connection with an empty GUC. Under the fail-closed policy those queries return rows only because of app-level `tenant_id` filters; RLS contributes no defense-in-depth, which is exactly the condition #1615 calls the vulnerability.

Whether a representative sample is enough depends on what closing #1615 means. #1615 is filed CRITICAL and its premise is "any missed filter in any route leaks cross-tenant data." A fix that protects 4 routes leaves the other ~386 with the same missed-filter exposure — the risk is unchanged for the bulk of the surface. Converting a representative sample demonstrates the mechanism; it does not remediate the defect. My decisive judgment: this PR is **not** sufficient to close #1615. To close it, the full tenant-data read surface must be wrapped — practically, all ~390 `requireAuth`/`requireTenantCtx` route files plus the `app/tenant/**/page.tsx` server pages. If mass-converting all of them in one PR is genuinely too risky to review (a defensible position), the correct outcome is to land this PR as "pinning mechanism + pilot conversions" and keep #1615 **open** with a tracked conversion checklist — not to close #1615 on the strength of 4 conversions. What is not acceptable is closing a CRITICAL isolation bug while ~386 routes and every server page remain in the defective state the issue describes.

The Server Component side is worse than the API side: `withTenantScope` exists but is called nowhere, so pages like `app/tenant/contacts/page.tsx`, `app/tenant/deals/page.tsx`, and `app/tenant/dashboard/page.tsx` — which render tenant data directly — run every query unpinned. Those are high-value read paths and are entirely unprotected by RLS in this PR.

### Tests now drive a real wrapped path

`with-api-route.test.ts` mocks only `pool.connect` and exercises the real `withPinnedConnection` + `withApiRoute`, asserting `getPinnedClient()` is the fake client both during "auth" and during the handler's later query. On the pre-fix (unwrapped) code that second assertion is `undefined`, so the test fails if the fix is reverted — the fail-without/pass-with property v1's tests lacked. It also confirms `release` fires once, the GUC-reset query is issued, params/request pass through, thrown errors propagate while still releasing, and the PgBouncer path pins nothing. All 25 unit tests across the four files pass here, with a clean typecheck and `eslint --max-warnings=0`.

The DB-free test is a valid stand-in for the self-skipping live-DB test for what it can prove — that the wrapper establishes and tears down the pin around the whole body — because pinning presence, not row visibility, is the behavior under test. It cannot prove RLS actually filters rows (that needs Postgres with the policies applied); the integration test's new `withApiRoute`-wrapped, filter-less-SELECT case covers that and self-skips without a DB. Not tested: any actual converted production route file end-to-end — the wrapper-shaped integration case is a proxy, so a regression in a specific converted route's export form would not be caught by these tests.

### Pool reset and swallowed GUC-reset (v1 #3) resolved

`lib/db/pool.ts` registers `pool.on('release')` under `if (!pgBouncer)` and re-resets the tenant GUCs unconditionally on every release, so the swallowed reset in `withPinnedConnection`'s `finally` cannot return a tenant-scoped connection to the pool on the default path — the safety condition v1 flagged holds. With per-request pinning this handler now fires once per request (on the single release) rather than once per query.

### Converted routes are pure rewraps

The four converted files change only the export form (`export async function GET` → `export const GET = withApiRoute(async ...)`) and the closing brace/paren; handler bodies, try/catch, rate-limit calls, and response shapes are untouched. The `[id]` route's `{ params }` second argument is forwarded through the generic unchanged.
