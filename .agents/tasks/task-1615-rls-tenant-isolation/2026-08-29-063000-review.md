# Full tenant-data surface pinned for RLS: withApiRoute across all 388 auth routes + withTenantScope across all 23 server pages (v3)

This pass applies the `withApiRoute` / `withTenantScope` wrappers (proven correct in v2) to the entire authenticated request surface: all 388 `app/api/**/route.ts` files that call `requireAuth` are now exported as `withApiRoute(async (...) => {...})`, and all 23 `app/tenant/**/*.tsx` server pages/layouts that call `requireTenantCtx` wrap their body in `withTenantScope(async () => {...})`. The conversion is a pure export-form rewrap — handler bodies, try/catch, rate-limiting, response shapes, dynamic-route `{ params }` types, and route-segment config exports are untouched — so every handler/page `db` query now runs on the same pinned connection that `setTenantContext()` wrote the tenant GUC on, making RLS functional defense-in-depth on the default non-PgBouncer deploy. A new test drives the _real_ exported route to prove pinning end-to-end, and the previously dead `withTenantScope` is now live.

Watch for: nothing blocking. The skip list (~95 public/webhook/auth/cron/SCIM routes + `logs/stream`) is safe by design — none of those routes call `setTenantContext`, so they never establish the tenant GUC that RLS keys off and pinning would add nothing (**confirmed**). The `dashboard/route.ts` alias now passes `undefined` as the second handler arg to match the widened signature, inheriting the pin from the wrapped `stats` route (**confirmed**). The `RouteHandler` return-type widening to `Response | undefined | void` is a safe superset with no call-site impact (**confirmed**).

**Verdict**: APPROVED

## High-level view

The v2 blocking finding was coverage: the mechanism was correct but only 4 of ~485 routes and 0 server pages were converted, leaving the bulk of the tenant-data surface running handler queries on unpinned, empty-GUC connections. v3 closes that completely. A `grep` for `requireAuth` route files lacking `withApiRoute` returns zero; a `grep` for `requireTenantCtx` pages lacking `withTenantScope` returns zero. Every request path that establishes a tenant GUC now encloses its subsequent queries in the pin, so RLS blocks a filter-less cross-tenant read across the whole authenticated surface.

The security boundary is coherent because `setTenantContext` — the GUC RLS keys off — is called _only_ inside `requireAuth` and `requireTenantCtx`. Every route that calls those is now wrapped; every route that doesn't (public forms, webhook receivers, cron sweeps, SCIM, OAuth callbacks, `logs/stream`) never sets the GUC and relies on explicit `tenant_id` filters, so it was never an RLS surface and wrapping it would pin an empty-GUC connection to no effect. That makes the skip list defensible rather than a gap.

The rewraps are behavior-preserving at scale. Static routes, dynamic `[id]` routes (params type carried through the generic), multi-method files, files with `export const dynamic`/`runtime` route-segment config, and server pages that call `notFound()`/`redirect()` all convert mechanically; the Next.js control-flow throws propagate through `withPinnedConnection`'s try/finally unchanged because the finally only resets GUCs and releases — it never catches.

Test integrity holds. The 13 modified unit tests add the identical established request-connection mock already used in `auth-middleware-require-auth.test.ts` (stub `withPinnedConnection` to run the callback, `getPinnedClient => undefined`) — a harness accommodation for the absent pool, not a weakened assertion. The new `route-pinning-real-route.test.ts` imports the actual production `GET` and asserts a client is pinned at the point the route runs, releases once, and clears — it fails if the route is reverted to a bare export.

### v2 blocking finding is resolved: full authenticated surface is pinned

The v2 verdict hinged on one thing — closing a CRITICAL cross-tenant defect requires the whole tenant-data read surface enclosed in the pin, not a 4-route sample. v3 delivers exactly that, and it is verifiable mechanically rather than by inspection:

```
grep -rlE "requireAuth" app/api --include=route.ts | xargs grep -L "withApiRoute"   → 0 files
grep -rlE "requireTenantCtx" app/tenant --include=*.tsx | xargs grep -L "withTenantScope" → 0 files
```

388 `requireAuth` route files and 23 `requireTenantCtx` pages/layouts, all wrapped. Every one of those handlers' post-auth `db` queries now resolves through the proxy to the single client that `setTenantContext()` set the session GUC on, so the fail-closed RLS policy — inert on the non-PgBouncer path before this work — now filters cross-tenant rows even when a handler forgets its app-level `tenant_id` filter. That is the defense-in-depth #1615 requires, and it now holds across the surface the issue describes rather than a pilot slice.

### The skip list is safe because it maps exactly to the "no tenant GUC" boundary

The ~95 unwrapped route files show up in a naive `tenant_id`/`tenantId` grep, which initially looks like unconverted tenant-data routes. They are not. `setTenantContext` — the only thing that writes the `app.current_tenant` GUC RLS reads — is called solely inside `requireAuth` and `requireTenantCtx` (plus the three pilot files that already had it). A scan of all unwrapped routes for `setTenantContext` returns zero. Their `tenant_id` references are explicit filter columns resolved from webhook signatures, public tokens, cron all-tenant sweeps, SCIM bearer tokens, or OAuth callback state — never an RLS-backed GUC. Wrapping them would pin a connection whose GUC is empty, so RLS would deny every row (fail-closed) or, more precisely, contribute nothing because these flows never opted into RLS scoping in the first place. Skipping them is correct, not a hole.

`app/api/logs/stream/route.ts` sits in this set for the same reason: it authenticates with `verifyToken` directly, does a single superadmin lookup keyed by `payload.userId` (not tenant-scoped data), sets no tenant GUC, and streams server logs. It is not a tenant-data path, and leaving it unwrapped is the right call — wrapping a long-lived SSE stream in a pinned connection would in fact be worse, holding a pooled client open for the stream's lifetime. The superadmin check running on an unpinned connection is fine because it reads a global `users` row by primary key, not RLS-scoped tenant data.

### Rewraps are behavior-preserving across every shape sampled

The dynamic `[id]` conversion carries the params type through the generic verbatim:

```
-export async function GET(req, { params }: { params: Promise<{ id: string }> }) {
+export const GET = withApiRoute(async (req, { params }: { params: Promise<{ id: string }> }) => {
```

Route-segment config exports (`export const dynamic`, `export const runtime`) are module-level exports independent of the handler, so rewrapping the handler export leaves them intact — confirmed on `metrics`, `openapi`, `system/ready`, and `logs/stream` (the ones that carry them). Multi-method files convert each method independently. Server pages wrap the entire body — including `await params` and the `requireTenantCtx()` call — inside the `withTenantScope` closure, so a `notFound()` in `companies/[id]/page.tsx` (`if (!company) notFound()`) throws the Next.js control-flow signal, which unwinds through `withPinnedConnection`'s finally (GUC reset + release, no catch) and re-propagates unchanged. The framework never sees altered behavior.

The one non-mechanical file is `app/api/tenant/dashboard/route.ts`, an alias that delegates to the wrapped `stats` `GET`. It stays a bare `export async function` (it does no auth or query itself) but now calls `getStats(request, undefined)` — passing the second arg the widened signature expects — and inherits the pin from the already-wrapped `stats` route. Correct: double-wrapping would be redundant and the reuse path would no-op it anyway.

### RouteHandler return type widened to Response | undefined | void

The type-only change from `Promise<Response> | Response` to `Promise<Response | undefined | void> | Response | undefined | void` accommodates fall-through/alias handlers that don't always return a `Response`. This is a superset of the previous type, so no existing handler stops type-checking, and Next.js already tolerates handlers that return `undefined`/`void` for methods like `OPTIONS`. `npm run typecheck` and `npx eslint . --max-warnings=0` both exit 0 over the full converted surface, which is the meaningful assurance here — 388 rewraps type-check clean.

### Tests: the 13 modified files are accommodated, not weakened; the new test is real

Each of the 13 updated unit test files adds the same block, identical to the pattern already established in `auth-middleware-require-auth.test.ts`:

```
vi.mock('@/lib/db/request-connection', () => ({
  withPinnedConnection: <T>(fn: () => Promise<T>): Promise<T> => fn(),
  getPinnedClient: () => undefined,
}));
```

These tests invoke converted handlers directly, and the handlers now route through `withPinnedConnection`, which needs a real pool the unit environment doesn't have. Stubbing it to run the callback directly preserves the exact behavior the tests already asserted (queries fall through to the pool-bound `db`); no assertion about tenant filtering, response shape, or query composition is relaxed. This is a harness fix for the wrapper, not a paper-over.

`route-pinning-real-route.test.ts` is the meaningful addition v2 asked for. It imports the real exported `GET` from `app/api/tenant/analytics/stats/route.ts`, mocks only `pg`'s `pool.connect`, and snapshots `getPinnedClient()` inside the `requireAuth` mock (the route's first call). On the pre-fix bare-export route that snapshot is `undefined` and `toBe(fakeClient)` fails; on the wrapped route it passes. It also asserts the response is preserved and the client releases exactly once with the pin cleared afterward. Reverting the route's export form breaks this test — the regression guard for a specific production route that the synthetic `with-api-route.test.ts` couldn't provide.

Validation run here: `npm run typecheck` exit 0, `npx eslint . --max-warnings=0` exit 0, and the pinning-related unit files (`route-pinning-real-route`, `with-api-route`, `request-connection`, `db-proxy-pinning`, `leads-route-filters`) 18/18 pass. The live-DB `rls-connection-affinity` integration test self-skips without Postgres, as expected in this sandbox.
