# Per-request connection pinning for RLS tenant isolation (v1)

Issue #1615 reports that Postgres RLS is effectively non-functional in the default (non-PgBouncer) deploy: `setTenantContext()` sets the tenant GUC as a session variable on whatever pooled connection the single `set_config` statement grabbed, that connection is released immediately, and each subsequent `db` query checks out a _different_ connection whose GUC is empty — so the fail-closed policy denies every row and tenant isolation rests entirely on app-level `tenant_id` filters. This change introduces an `AsyncLocalStorage`-based pinning primitive (`withPinnedConnection`/`getPinnedClient`) that checks out one `PoolClient` for a scope, and rewires the global `db` proxy to route queries to the pinned client when one is present. The pin is applied inside `requireAuth()` and `requireTenantCtx()`, and is a no-op under PgBouncer.

Watch for: the pin is established _inside_ the auth helpers, which return before route handlers run their own data queries — so the actual attack surface described in #1615 (handler-level queries with a missing `tenant_id` filter) remains on unpinned pool connections and unprotected by RLS (**confirmed**). The pinning primitive itself is correct and well-tested, but the fix does not close the defect it targets.

**Verdict**: NEEDS_CHANGES

## High-level view

The pinning primitive is sound: one client per async scope via `AsyncLocalStorage`, nested calls reuse the existing pin, GUCs are reset and the client released in a `finally` block on every exit path including throws, and the PgBouncer path short-circuits before acquiring anything. The `db` proxy resolves per-property-access to the pinned client's drizzle instance (WeakMap-cached) or the pool-bound instance; because resolution reads the ALS store on each access, concurrent requests each see their own pinned client with no cross-context sharing.

The problem is scope, not mechanism. `AsyncLocalStorage` scopes are lexical, and the pin lives inside `requireAuth()`/`requireTenantCtx()`. The dominant call pattern across ~388 route files is `const ctx = await requireAuth(request); ...db queries...` — the handler's queries execute _after_ `requireAuth` has returned and its ALS scope has closed, so they fall back to the pool-bound (unpinned) `db`. Those handler queries are exactly the ones #1615 says leak when an app-level filter is missing. The fix makes RLS functional for the auth/context lookups themselves, but leaves the handler query surface — the actual defect — unprotected by RLS.

The author documents this residual honestly in the module header and DEPLOYMENT.md, and argues editing every route is out of scope and that Next.js App Router offers no per-request hook. That framing is reasonable on effort, but it means the change does not satisfy #1615's explicit acceptance criterion: prove RLS blocks a cross-tenant handler read with app-level filters removed. The live-DB proving test demonstrates isolation only _inside_ an explicit `withPinnedConnection` block that no production handler actually enters.

### The pin covers the auth helpers, not the handler queries #1615 is about

This is the blocking concern. `requireAuth()` wraps its body in `withPinnedConnection(...)` and returns the resolved `AuthContext`. The `finally` in `withPinnedConnection` resets the GUCs and releases the client _as `requireAuth` returns_, tearing down the ALS scope. Every route handler then runs like this (`app/api/admin/flags/route.ts`, representative of ~388 files):

```
const ctx = await requireAuth(request);   // pin acquired AND released here
if (ctx instanceof NextResponse) return ctx;
const flags = await getAllFlags();         // runs on an UNPINNED pool connection
```

By the time `getAllFlags()` (or any `db.select`/`db.execute` in the handler) runs, `getPinnedClient()` returns `undefined`, so the proxy routes to the pool-bound instance — a fresh connection with an empty tenant GUC. Under the fail-closed policy that connection sees zero tenant rows, so these handler queries _must_ still carry an app-level `tenant_id` filter to return anything. The RLS layer contributes no defense-in-depth to them, which is precisely the state #1615 describes as the defect ("any missed filter in any route leaks cross-tenant data"). A documented residual that coincides with the issue's core requirement is not the same as fixing the issue.

There is a sound minimal path the author dismisses too quickly. Next.js has no framework-level per-request hook, but the codebase already funnels every API route through `requireAuth(request)` and every Server Component through `requireTenantCtx()`. A shared route wrapper — `export const GET = withApiRoute(async (request, ctx) => { ... })` where `withApiRoute` runs `withPinnedConnection(() => { const ctx = await requireAuth(request); ...; return handler(request, ctx); })` — encloses both the auth path and the handler queries in one pinned scope, and migrating routes to it is mechanical. That is a larger change than this PR, but it is the change #1615 asks for. Wrapping only the auth helper does not move the needle on the reported vulnerability.

### Pinning primitive: reset/release on error paths and nesting

The primitive itself is correct. The two failure-mode details worth noting: the `finally` block issues the tenant-GUC reset and releases the client on every exit — happy path, a throw from `fn`, and a throw from the reset query (swallowed). If `getPool().connect()` itself fails, the error propagates without entering a scope and the request falls back to the pool-bound (fail-closed) db — acceptable, no leaked connection. Nested calls reuse the existing pin rather than acquiring a second connection, so the release fires exactly once when the outer scope unwinds; the test confirms `connect`/`release` are each called once across nesting.

On issue #3: the reset in `finally` is wrapped in `try/catch {}` and swallows any error before `client.release()`. That swallow is safe _only if_ the pool's own `release` handler re-resets unconditionally on the non-PgBouncer path. `lib/db/pool.ts` registers `pool.on('release', ...)` under `if (!pgBouncer)`, so on the default path it does fire and a swallowed reset here cannot leak a tenant-scoped connection. The safety of the swallow depends on that second reset existing — worth a glance during any future pool-wiring refactor.

### Proxy routing and concurrency safety

`resolveDb()` reads `getPinnedClient()` on every proxy property access and returns either the WeakMap-cached drizzle instance bound to that client or the shared pool instance. Because the pinned client is read from the ALS store per access rather than captured once, two concurrent requests — each in its own `withPinnedConnection` scope — resolve to their own client; there is no shared-client hazard across async contexts. `db-proxy-pinning.test.ts`'s "always resolved to pool" assertion is exactly what would fail on the reverted code, so the unit proof is meaningful.

### Test coverage

The unit tests (`request-connection.test.ts`, `db-proxy-pinning.test.ts`) are DB-free and would fail if the fix were reverted: the proxy test's `!== 'pool'` assertion under a pinned client, and the primitive test's acquire/reset/release/nesting/no-op assertions. All 20 unit tests pass here, alongside a clean typecheck and `eslint --max-warnings=0`. The PgBouncer no-op path is covered.

Not tested: any actual route handler under RLS. The live integration test (`rls-connection-affinity.test.ts`) self-skips without Postgres (expected in the sandbox) and, even when it runs, asserts isolation only inside a hand-written `withPinnedConnection` block. Nothing exercises the real `requireAuth → handler query` sequence, so no test would catch that handler queries run unpinned. Since #1615's acceptance criterion is specifically "RLS blocks a cross-tenant read with app-level filters removed" in a real request path, that gap is the test-level manifestation of issue #1.
