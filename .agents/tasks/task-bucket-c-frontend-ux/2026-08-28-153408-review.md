# Bucket C — frontend/UX polish, code-quality sweep, and PII-in-logs hardening (v1 review)

Six change sets land the Bucket C work: themed dialogs and dark-mode error page (FEAT-002), standardized skeletons plus chart/builder ErrorBoundary wrapping and router-based navigation (FEAT-003), a new zod-validated leads filter API and UI (FEAT-004/#1083), a bounded code-quality sweep removing the `Window` index-signature, routing dashboard `console.error` through `logError`, typing 19 `any` offenders and adding AbortController cleanup to three loaders (FEAT-005), and PII hardening across the bulk-email worker, the Telegram bot webhook, and the WhatsApp lead-warming sender (FEAT-006). The priority for this pass is behavioral correctness, since the change touches a webhook control-flow path, Drizzle where-clause composition, client navigation semantics, and fetch lifecycle.

Watch for: an AbortController fail-open loading flicker where an aborted in-flight fetch still runs `setLoading(false)` on a remounted component (likely); the SMS form submits the raw, un-normalized phone string after validating a normalized copy (possible); the command-palette "Super Admin" entry now does a client-side `router.push` across the tenant→superadmin app boundary instead of a hard reload (possible). Telegram webhook still returns 200 promptly, tenant-scoping on the new leads filters is intact, and no raw email/token is logged — all confirmed.

**Verdict**: APPROVED

## High-level view

The Telegram webhook change makes `sendReply` awaited so rate-limit and network failures are logged instead of swallowed. The await is bounded by the existing 10s `AbortSignal.timeout`, and every handler still returns `NextResponse.json({ ok: true })` immediately after a single bounded send, so the webhook remains responsive and produces no unhandled rejections.

The new leads filters (source, lifecycle_stage, assigned_to, tags, score_min/score_max) are validated with zod and composed into the existing `and(...filters)` array that already carries the `tenantId` and soft-delete predicates plus the row-level `view_all` restriction. Tenant scoping and permission scoping are preserved; column types line up (`tags` is `text[]` → `arrayContains`/`@>`, `score` is integer → `gte`/`lte`). The where-clause assembly is not covered by any route-level test.

The AbortController additions correctly swallow `AbortError` to suppress spurious error toasts, but the shared `finally { setLoading(false) }` runs even for an aborted request. On a dependency change (offset/filter), the old fetch's abort resolves after the new fetch has set loading true, briefly clearing the spinner while the new request is still in flight.

The `router.push` conversions in the command palette and deals kanban are in-app tenant navigations and are a strict improvement over `window.location.href`, with one exception worth a look: the "Super Admin" palette entry crosses into the `/superadmin` app segment via a client-side transition.

The PII work redacts recipient emails in the BullMQ result set, drops the raw email from the Telegram `/info` reply, redacts pending-tenant billing emails, and surfaces a stale/expired WhatsApp token (401 / Meta codes 190/102/463) as a structured operator-actionable error while preserving the existing no-requeue delivery-safety behavior.

The `Window` index-signature removal restores real type-checking for `window.*` access; the only two app-injected globals (`__NUCRM_PLAN_FEATURES__`, `__NUCRM_IS_SUPER_ADMIN__`) are now explicitly declared and typecheck is green.

### Awaited Telegram sendReply keeps the webhook responsive

`sendReply` changed from fire-and-forget `fetch().catch(console.error)` to an awaited call that logs non-2xx responses (Telegram 429 rate-limits) and network errors through `logError`. The 10s `AbortSignal.timeout` is retained, so a handler blocks on at most one bounded send before returning `NextResponse.json({ ok: true })`, and every call site awaits so there is no dangling promise or unhandled rejection. The trade-off: a slow-but-under-10s Telegram API now delays the webhook response by that duration where previously it returned instantly — acceptable for a bot webhook and bounded by the timeout.

### Leads filter composition preserves tenant and permission scoping

The parsed filters are pushed onto the same `filters` array seeded with `eq(leads.tenantId, ctx.tenantId)`, `isNull(leads.deletedAt)`, and — for users lacking `leads.view_all` — the `or(assignedTo=me, createdBy=me)` restriction, then applied with `and(...filters)` to both the count and data queries. Column mapping checks out: `tags` is `text('tags').array()` so `arrayContains(leads.tags, tagList)` emits the `@>` contains-all semantics the comment promises; `score` is `integer` so `gte`/`lte` are correct; `source` maps to the `lead_source` column via the schema alias. The comma-split trims and drops empties, and an empty `assigned_to` (`z.literal('')`) is skipped by the `if (assignedTo)` guard rather than filtering on an empty UUID.

The gap is test depth: `tests/unit/schemas.test.ts` covers coercion and rejection at the schema layer, but nothing exercises the route's where-clause assembly — a contains-all tag query or a `score_min`/`score_max` window could regress without a failing test.

### AbortController cleanup swallows AbortError but shares the loading finally

```js
const load = useCallback(async (signal?: AbortSignal) => {
  setLoading(true);            // (present in follow-ups/activities; notifications sets it once)
  try {
    const res = await fetch(url, { signal });
    ...
  } catch (err) {
    if (err instanceof DOMException && err.name === 'AbortError') return;
    toast.error(...);
  } finally {
    setLoading(false);         // runs even when the request was aborted
  }
}, [deps]);

useEffect(() => {
  const c = new AbortController();
  load(c.signal);
  return () => c.abort();
}, [load]);
```

When the effect re-runs because a dependency changed (offset paging, status filter), cleanup aborts the old request, the new effect sets loading true, then the _old_ request's rejection settles and its `finally` sets loading false — while the new request is still outstanding. The result is a spinner that flickers off mid-load. On unmount this is harmless (React no-ops the state set), but the dependency-change path is the common one for these paged list views. Guarding with `if (!signal?.aborted) setLoading(false)` closes it.

### router.push conversions and the superadmin boundary

The command palette moved from encoding destinations inside `onClick: () => window.location.href = ...` — and reverse-parsing the href back out of `onClick.toString()` for the recents list, a genuinely fragile pattern — to a declarative `href` field dispatched through a single `runItem`/`router.push`, dropping the stringified-function regex entirely. Deals-kanban card clicks and edit menu items likewise move to `router.push('/tenant/deals/${id}')`.

The one entry that crosses an app boundary is the "Super Admin" palette item, now `router.push('/superadmin/dashboard')` from a tenant context. If the `/superadmin` segment mounts under a different layout root or performs a server-side auth gate that a client transition bypasses or renders inconsistently, this is a behavioral regression versus the prior hard reload. Worth confirming the superadmin dashboard renders correctly when reached via client push; if not, that single item should retain a hard navigation.

### SMS validation normalizes for the check but submits the raw value

The submit guard normalizes the number (`form.to.replace(/[\s()-]/g, '')`) and tests it against `/^\+?\d{7,15}$/`, then sends `{ to: form.to }` — the original, un-normalized string. A number entered as `+1 (555) 012-3456` passes the check but transmits the formatted string to the API. If the SMS backend expects E.164 this will fail server-side or at the provider despite passing client validation. Sending `normalizedTo` makes the client validation and the payload consistent.

### PII redaction across worker, Telegram, and WhatsApp

The bulk-email worker stores `redactEmail(recipient.email)` in the per-recipient result object BullMQ persists to the Redis completed set, on both success and failure branches. The Telegram `/info` reply replaces the echoed email with "linked to your account", and the pending-tenants listing redacts `billingEmail` — `redactEmail` guards null/empty internally, so dropping the prior `|| 'N/A'` is safe.

The WhatsApp lead-warming sender classifies HTTP 401 or Meta OAuth codes 190/102/463 as an expired/revoked token and logs it via `logError` with an operator-facing message and structured metadata (integration id, status, Meta code), prefixing the persisted `errorMessage` accordingly. The claim is still released to `failed` (not requeued) exactly as before, so the existing delivery-safety reasoning holds; only diagnostics changed. Automatic token refresh is documented in-code as a follow-up.
