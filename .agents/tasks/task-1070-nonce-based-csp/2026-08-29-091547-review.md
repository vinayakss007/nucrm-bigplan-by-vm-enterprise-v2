# Nonce-based CSP to drop `script-src 'unsafe-inline'` (v1)

The proxy (Next 16 middleware, `proxy.ts`) now mints a per-request base64 nonce, builds the whole Content-Security-Policy in one place, and layers it onto HTML page navigations only. The nonce is written to both the _forwarded request_ `content-security-policy` header (so Next 16 app-render stamps `nonce=` onto its framework/hydration/injected scripts) and the _response_ headers, plus an `x-nonce` header the branding server components read. `script-src 'unsafe-inline'` is gone in favour of `'nonce-<value>'` (prod) / `+'unsafe-eval'` (dev). The static CSP headers in `next.config.mjs` and `nginx.conf` were removed so `proxy.ts` is the single source of truth. `style-src 'unsafe-inline'` is deliberately retained (next/font, react-hot-toast, tenant branding) and documented.

Watch for: the nginx CSP that was removed carried `img-src ... https:` and `frame-ancestors 'self'`, both broader than the new proxy policy — the effective policy tightens, which can break third-party `https:` images if nginx's header was ever the enforced one (**likely**). The whole change hinges on an operator dependency that no code can enforce: any nginx/CDN/WAF that sets or strips CSP silently re-opens the gap (**confirmed**, documented). `docs/SECURITY-ANALYSIS.md` is 259 lines of churn that is almost entirely prettier table/code reformatting bundled into a security fix (**confirmed**).

**Verdict**: APPROVED

## High-level view

The Next 16 nonce contract is wired correctly. The nonce is base64 of a random UUID, which stays inside Next's `/^'nonce-([A-Za-z0-9+/_-]+={0,2})'$/` charset, and it is set on the forwarded request header under the exact name (`content-security-policy`) app-render reads, so hydration/framework scripts get stamped. The same CSP and an `x-nonce` header ride the response for browser enforcement.

Every other directive is byte-for-byte identical to the previous `next.config.mjs` production policy — realtime `ws:`/`wss:`, `img-src data: blob:`, `worker-src blob:`, and the hardened `object-src 'none'`/`base-uri 'self'`/`frame-ancestors 'none'` are all preserved. The only relaxation is dev-only `'unsafe-eval'`.

`/api/` responses never receive the page CSP: both the public-page and authenticated-pass-through branches guard on `isApiRequest(pathname)`, and the API branches return plain `NextResponse.next()`. Existing auth/rate-limit/CSRF/CORS/`x-request-id` logic is untouched — the nonce is layered only onto the two page-navigation `NextResponse.next()` sites.

The two removed static CSP headers are the right call for single-source-of-truth, but the nginx variant was a _superset_ on `img-src` (`https:`) and looser on `frame-ancestors` (`'self'`), so the net effect is a tightening whose runtime impact can only be verified against a live host.

`style-src 'unsafe-inline'` retention is justified and documented in three places; the first-party branding `<style>` still gets a nonce as defense-in-depth. The branding components were made async and only `BrandingProvider` has a caller (`app/tenant/layout.tsx`, already an async server component), so `headers()` is safe there. Runtime CSP-violation checks (hydration, toasts, fonts, websocket, Sentry) are documented as manual steps, not executed — the residual risk lives entirely in that unrun verification.

### Next 16 nonce contract wiring

`nextWithCsp` clones the incoming headers, sets `content-security-policy` and `x-nonce` on that clone, and hands it to `NextResponse.next({ request: { headers } })` — the shape app-render inspects — then echoes the same CSP onto the response so the browser enforces the policy the page was rendered against. The header name is lowercase, matching the case-insensitive read in Next's `get-script-nonce-from-header`.

The nonce is `Buffer.from(globalThis.crypto.randomUUID()).toString('base64')`. Base64 of a UUID produces `[A-Za-z0-9+/]` with up to two `=` of padding, all inside Next's `/^'nonce-([A-Za-z0-9+/_-]+={0,2})'$/`.

`nextWithCsp` fires for every non-API page request reaching the two pass-through sites, including RSC/prefetch navigations, each getting a fresh nonce and a CSP header on the response — it is not narrowed to full-document loads. Harmless for RSC payloads (no inline `<script>` to authorize), but the scope is worth noting if response-header size or caching behavior on RSC responses ever matters.

### Directive parity and the removed static headers

The proxy policy is byte-for-byte the old `next.config.mjs` production CSP with only `script-src` changed, and a test asserts each hardened directive is present. The nginx header that was removed was _not_ identical to the app policy:

```
# old nginx.conf CSP (removed)
... img-src 'self' data: blob: https: ; ... frame-ancestors 'self'; base-uri 'self'; form-action 'self'
# (no frame-src, object-src, worker-src)
```

versus the proxy's `img-src 'self' data: blob:` (no `https:`) and `frame-ancestors 'none'`. With both `next.config.mjs` and nginx previously emitting CSP, browsers enforce the intersection of duplicate headers, so the effective prior image policy already excluded `https:` unless nginx's header alone reached some path the Next header did not. The `img-src https:` removal is the one place a previously-loading external image could now be refused — confirm on a live tenant page since it can't be checked here.

### `/api/` isolation

The public-page branch (`!isApiRequest && isPublic`) and the authenticated tail (`isApiRequest(pathname) ? NextResponse.next() : nextWithCsp(request)`) both gate the CSP behind a non-API check, and every API branch — public rate-limited, csrf-token, bypass, `ak_` key pass-throughs, 401/403/429 error builders — returns responses that never touch `nextWithCsp`. Tests assert both a public `/api/` and an authenticated `/api/` response carry neither `content-security-policy` nor `x-nonce`.

### Branding components and `headers()`

`BrandingProvider`'s only caller is `app/tenant/layout.tsx`, itself an async server component, so awaiting `headers()` is safe and the tenant `<style>` is nonced. `BrandedHeader` has no current callers, so its async conversion is inert today; if it is later dropped into a non-async or client boundary the `await headers()` forces a server-component contract on the consumer — a latent constraint, not a current bug. CSS sanitization is unchanged in both. Because `style-src` still allows `'unsafe-inline'`, the nonce on these `<style>` tags does not gate rendering; it is defense-in-depth only.
