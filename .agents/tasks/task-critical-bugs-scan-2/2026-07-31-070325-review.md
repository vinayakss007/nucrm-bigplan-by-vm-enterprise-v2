# Critical bug fixes: auth bypass, deal counters, email compliance, SSRF, CSRF, Stripe plan detection, and counter drift across multiple paths

This PR applies nine targeted fixes from the initial scan plus seven additional counter-drift and data-exposure fixes discovered during review. The original fixes address: API key expiration bypass, deal counters never decrementing on delete, AuthContext.user not populated for normal users, bulk email ignoring doNotContact, an open redirect in email click tracking, SSRF in automation webhooks, fragile Stripe plan detection, and CSRF bypass on forgot-password. The additional fixes close counter drift gaps in contacts bulk delete, trash restore, deals import, lead conversion, form submission, contacts merge, and restrict the public invoices endpoint from exposing sensitive fields.

Watch for: The deal counter decrement on single delete is not wrapped in the same transaction as the soft-delete itself (confirmed), creating a window where a crash between the two statements leaves counters permanently drifted. The SSRF blocklist uses hostname string matching, which DNS rebinding can bypass (likely).

**Verdict**: APPROVED

## High-level view

The API key auth fix is a single guard that returns null when `expiresAt` is in the past. An expired key that was never deactivated was silently passing authentication.

Deal counter drift is fixed in both single-delete and bulk-delete paths by decrementing `currentDeals` using `greatest(0, currentDeals - N)`. The fix does not wrap the decrement in the same transaction as the single-deal soft-delete, leaving a residual atomicity gap (the contacts DELETE does this correctly by contrast).

Counter drift was pervasive: contacts bulk delete never decremented `currentContacts`, trash restore never re-incremented either counter, deals import never incremented `currentDeals`, lead conversion never incremented either counter when creating new records, form submission never incremented `currentContacts`, and contacts merge never decremented when soft-deleting the duplicate. All seven paths are now fixed.

The public invoices endpoint (`/api/public/invoices`) previously returned full invoice records — including internal notes, payment references, and all metadata — to anyone providing a contact's email address. It now returns only safe fields (invoice number, status, amounts, dates) and only for invoices with status sent/paid/overdue/partially_paid.

Bulk email endpoints now filter `doNotContact = false`, preventing sends to unsubscribed contacts. The click-tracking endpoint validates redirect URLs against protocol and hostname blocklists.

The automation engine's `fire_webhook` validates target URLs against private IP ranges and reserved hostnames before fetching. The check is string-based (no DNS resolution), which stops naive SSRF but not DNS rebinding.

Stripe plan detection falls through three strategies: expanded subscription → line*items price ID → amount heuristic. Misconfigured `STRIPE_PRICE*\*` env vars cause silent fallback to the fragile heuristic with no runtime warning.

CSRF validation is now required for `/api/auth/forgot-password`.

<summary>Issues (4)</summary>

1. **Deal counter decrement not transactional** — The single-deal DELETE decrements `currentDeals` as a separate statement outside the transaction. A crash between the two leaves the counter permanently drifted. Wrap both in a single transaction (the contacts DELETE already does this correctly).
2. **SSRF blocklist bypassed by DNS rebinding** — `isAllowedWebhookUrl` checks the hostname string but does not resolve DNS. An attacker-controlled domain resolving to `169.254.169.254` at fetch time passes the check. Consider resolving DNS or using an egress proxy.
3. **Stripe fallback heuristic still reachable** — When `STRIPE_PRICE_*` env vars are not configured, all price IDs return null and the amount heuristic runs silently. Add a log warning when the heuristic activates.
4. **IPv6 loopback in click tracking blocklist** — The blocklist entry `[::1]` includes brackets, but `URL.hostname` strips them for IPv6. The entry should be `::1` without brackets to match correctly.

## Deal counter decrement is not atomically paired with the soft-delete

In `app/api/tenant/deals/[id]/route.ts`, the DELETE handler first performs the soft-delete (`UPDATE deals SET deleted_at = now() ... RETURNING`), then on a subsequent statement decrements `currentDeals`. If the process crashes or the second statement times out, the deal is deleted but the counter never decrements. Contrast with the contacts DELETE in `app/api/tenant/contacts/[id]/route.ts` which correctly wraps both operations inside `db.transaction(async (tx) => { ... })`.

The bulk-delete path in `app/api/tenant/deals/bulk/route.ts` has the same structure.

```typescript
// deals/[id]/route.ts – counter update is outside any transaction
const [row] = await db.update(deals).set({ deletedAt: new Date(), ... }).returning({ id: deals.id });
if (!row) return ...;
// ← crash here leaves counter drifted
await db.update(tenants).set({ currentDeals: sql`greatest(0, ...)` }).where(...);
```

## Counter drift across seven additional paths

The `currentContacts` and `currentDeals` tenant counters are used for plan limit enforcement. Before this fix, six paths modified these entities without updating the counters:

- **Contacts bulk delete** (`contacts/bulk/route.ts` delete case): soft-deleted contacts but never decremented `currentContacts`
- **Trash restore** (`trash/route.ts` PATCH): restored contacts/deals from trash without re-incrementing their respective counters
- **Deals import** (`deals/import/route.ts`): batch-inserted deals without incrementing `currentDeals`
- **Lead conversion** (`leads/[id]/convert/route.ts`): created new contacts and deals inside the transaction without updating either counter
- **Form submission** (`forms/submit/route.ts`): created new contacts from public form submissions without incrementing `currentContacts`
- **Contacts merge** (`contacts/merge/route.ts`): soft-deleted the duplicate contact without decrementing `currentContacts`

Each of these causes the counter to drift from reality. Over time, this means plan limits either block users too early (if decrements are missed) or allow over-provisioning (if increments are missed). The fixes mirror the existing patterns: `greatest(0, counter - N)` for decrements, `counter + N` for increments.

## Public invoices data exposure

The `/api/public/invoices` endpoint accepted an email address as a query parameter and returned full invoice records via `db.select()` with no column restriction. This exposed: internal `notes`, `terms`, `footer`, `paymentReference`, `paymentMethod`, `createdBy`, `updatedBy`, `metadata`, and all other columns to any unauthenticated caller who knows a contact's email address.

The fix restricts the returned columns to safe public-facing fields and filters to only return invoices that have been explicitly sent to the client (status in `sent`, `paid`, `overdue`, `partially_paid`). Draft and cancelled invoices are no longer visible.

## SSRF protection: hostname-only check

The `isAllowedWebhookUrl` function parses the URL and checks the hostname string against known private ranges and blocklisted names. This correctly blocks `http://169.254.169.254/...` and `http://localhost/...` but does not resolve DNS. A domain that returns a CNAME to `169.254.169.254` will pass. Standard limitation of client-side SSRF blocklists; residual risk, not blocking.

## Stripe plan detection fallback

`determinePlanFromCheckoutSession` tries three strategies. If the webhook payload arrives without subscription or line_items expansions, both strategies return null and the amount heuristic runs with no runtime signal. Silent fallback to a fragile path is a reliability risk.
