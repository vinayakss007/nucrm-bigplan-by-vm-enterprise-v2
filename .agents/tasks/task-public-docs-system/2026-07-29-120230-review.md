# Public documentation system for NuCRM marketing site

This change adds a complete public-facing documentation site under `/docs` in the marketing layout. It installs an MDX pipeline (@next/mdx + rehype-slug + rehype-pretty-code + remark-gfm), builds docs infrastructure (160-article tree definition, sidebar, breadcrumbs, prev/next, TOC, Cmd+K search), writes 30 MDX articles across four sections (Getting Started, Contacts, Deals, Communication), and removes the old `/docs` page that leaked tech-stack internals. The approach is client-rendered MDX via dynamic `import()` with a static params manifest for SSG route generation.

**Watch for:** The dynamic MDX import in `MDXContent.tsx` defeats static pre-rendering — every article loads client-side even though `generateStaticParams` declares all routes (confirmed). The `rehype-autolink-headings` with `behavior: 'wrap'` conflicts with the custom `HeadingLink` component in `mdx-components.tsx`, producing doubled/nested anchor elements (confirmed). The article tree declares 160 articles but only 30 MDX files exist; the remaining 130 routes will hit the "coming soon" fallback client-side rather than 404ing at build time (confirmed).

## High-level view

The MDX pipeline is configured in `next.config.mjs` with remark-gfm, rehype-slug, rehype-autolink-headings, and rehype-pretty-code (one-dark-pro). The configuration works for build-time MDX compilation, but the runtime loading strategy bypasses it: `MDXContent.tsx` uses client-side `import()` which means pages render with a loading skeleton first, then hydrate MDX. This negates the SEO value of static generation for a documentation site.

The `DocsTableOfContents` uses IntersectionObserver to detect visible headings from the DOM after client render. Since MDX loads asynchronously, the TOC reads headings from an initial empty state and only updates on first mount — it never re-reads when content arrives.

Search operates against a pre-built in-memory index of all 160 declared articles (titles and section descriptions only, no full-text). The search index includes unpublished articles, so results frequently link to empty placeholder pages.

The article tree in `lib/marketing/docs.ts` declares 16 sections with 160 total articles but only 30 `.mdx` files exist across 4 sections. There is no build-time validation that declared articles have corresponding MDX files, and no visual distinction in the sidebar between published and placeholder content.

<details>
<summary>Issues (6)</summary>

1. **Client-side MDX defeats SSG** — `MDXContent.tsx` uses dynamic `import()` in a `useEffect`, so all article content renders client-side with a loading skeleton. Move to server-side MDX rendering (direct import in the `[...slug]/page.tsx` server component) to get static HTML at build time.
2. **Doubled anchor elements on headings** — `rehype-autolink-headings` with `behavior: 'wrap'` wraps heading text in an `<a>` tag, and then the custom `H2`/`H3` components append a second `<HeadingLink>` anchor. Remove either the rehype plugin's autolink or the custom HeadingLink.
3. **130 ghost articles in sidebar** — The tree declares 160 articles but only 30 MDX files exist. Users see sections and links that lead to "coming soon" placeholders. Either trim the tree to match existing content or add a visual indicator for unpublished articles.
4. **TOC never re-reads after async content mount** — `DocsTableOfContents` runs its heading scan in a `useEffect` with an empty dependency array. When MDX loads asynchronously after the TOC mounts, the heading list is stale (empty). Add a MutationObserver or a content-ready signal.
5. **CopyButton targets wrong element** — `CopyButton` uses `document.querySelector('.group:hover pre')` which queries globally for any hovered `.group` ancestor, not the specific code block it belongs to. Use a ref scoped to the parent container instead.
6. **No SSR-safe platform detection for Cmd+K hint** — `isMac` reads `navigator.platform` at render time without a hydration guard. This causes a hydration mismatch since the component is `'use client'` but still SSR-rendered initially.

## Client-rendered MDX vs. static generation mismatch

The `[...slug]/page.tsx` route uses `generateStaticParams` to declare every article for SSG, and the page itself is an async server component. But instead of importing MDX content at the server level, it delegates to `MDXContent.tsx` — a `'use client'` component that does:

```tsx
useEffect(() => {
  import(`@/content/docs/${sectionSlug}/${articleSlug}.mdx`).then((mod) =>
    setContent(() => mod.default),
  );
}, [sectionSlug, articleSlug]);
```

The server-rendered HTML for every docs page is just the breadcrumb, title, and a loading skeleton. The actual article body only appears after JavaScript executes on the client. For a public documentation site that needs indexing and fast first-paint, this defeats the purpose of SSG.

The fix is to import MDX at the server component level in `page.tsx`:

```tsx
const Content = (
  await import(`@/content/docs/${sectionSlug}/${articleSlug}.mdx`)
).default;
return <Content />;
```

This produces fully static HTML with zero client-side loading for content.

## Heading anchor collision

The `next.config.mjs` configures:

```js
[rehypeAutolinkHeadings, { behavior: 'wrap' }],
```

This wraps each heading's children in an `<a href="#id">` tag. Meanwhile, `mdx-components.tsx` defines custom `H2`/`H3`/`H4` overrides that append their own `<HeadingLink>` component — another `<a href="#id">`. The result is nested anchor elements: invalid HTML and confusing click targets.

## TOC timing issue with async MDX

`DocsTableOfContents` scans for headings on mount:

```tsx
useEffect(() => {
  const elements = Array.from(
    document.querySelectorAll(".docs-prose h2[id], .docs-prose h3[id]"),
  );
  // ...
}, []);
```

The empty dependency array means this runs once. But MDX content loads asynchronously via `MDXContent`, so when this effect fires, the `.docs-prose` container contains only the loading skeleton — no headings exist yet. The TOC stays empty until a full page navigation triggers a remount.

## CopyButton global query

```tsx
<CopyButton
  getText={() => {
    const el = document.querySelector(".group:hover pre");
    return el?.textContent ?? "";
  }}
/>
```

If multiple code blocks are visible, or if the hover state is lost between click and execution, this returns the wrong text or empty string. A ref-based approach scoped to the specific `<pre>` container would be reliable.

## Platform detection hydration mismatch

```tsx
const isMac =
  typeof navigator !== "undefined" &&
  /Mac|iPod|iPhone|iPad/.test(navigator.platform);
```

This executes during SSR (where `navigator` is undefined, so `isMac` = false) and again during hydration (where it may be true). The standard fix is to default to a neutral state and set the platform in a `useEffect`.

## 130 unpublished article stubs

The tree in `lib/marketing/docs.ts` declares 16 sections totaling 160 articles. Only 4 sections have MDX files (30 total). The remaining 12 sections (leads, tasks, automation, billing, support, analytics, AI, security, platform, integrations, industry, API) appear in the sidebar with all their articles listed and searchable. Clicking any of these 130 links renders the "coming soon" card — users can't distinguish between real content and placeholders without clicking through.
