Every line below is backed by a file:line citation, a CI result, or a register
entry (docs/infra/PREPROD-ISSUE-REGISTER.md = "PP-0NN"). Where the evidence is
only "the code exists", it says UNVERIFIED — that is not the same as working.

How to read the three layers:
  LAYER 1  STABLE        -> put in 1.0.0 and say it works.
  LAYER 2  TWEAK-FIRST   -> in 1.0.0, but only after the named one-line change.
  LAYER 3  HIDE          -> do NOT show in 1.0.0. Keep the code, ship it in 1.1/2.0.
                             "Hide" is mechanical here: module flag off via
                             lib/modules/gate.ts:28 / lib/auth/middleware.ts:444,
                             nav entry removed from components/tenant/layout/sidebar-nav.ts,
                             or the route stays but returns 404 for non-internal callers.

LAYER 3 — DO NOT SHOW IN 1.0.0. KEEP THE CODE, SHIP IT IN A LATER VERSION.
================================================================================
Hiding is not deleting. Each item below has a mechanical off-switch and a reason
that is about trust, not about effort.

3.1  AI module — HIDE ENTIRELY (nav + pages + settings entries).
     Why: no ANTHROPIC_API_KEY on any host, so every call degrades silently
     (PP-019); "Time saved — coming soon" at app/tenant/ai/page.tsx:83; an
     AiComingSoon stub rendered at app/tenant/settings/ai-activity; FIVE 'beta'
     badges at components/tenant/ai/ai-config.ts:63,72,81,98,107, rendered by
     app/tenant/ai/page.tsx:145, app/tenant/ai/layout.tsx:63-100,
     app/tenant/settings/page.tsx:210 and
     components/tenant/settings/settings-nav.tsx:149.
     A stable release cannot ship a surface that is credential-less, silently
     degraded, and calls itself beta.
     HOW IT GATES: module flag off via lib/modules/gate.ts:28 /
     lib/auth/middleware.ts:444 (registry lib/modules/registry.ts) and the AI
     entries dropped from components/tenant/layout/sidebar-nav.ts. Re-enable in
     1.1 with the key set and the badges removed.
     NOTE ON THE REGISTER: PP-040/PP-042 describe ai_providers as undeclared and
     unpoliced. That is stale — the table IS declared (drizzle/schema/ai.ts) and
     DOES have RLS with an intentional global read policy
     (drizzle/migrations/0115_rls_view_hardening.sql:60-62, rationale at :24-25).
     Re-measure before that claim is repeated anywhere.
3.2  External e-sign providers (DocuSign) — HIDE the provider selector.
     Why: DocuSignAdapter defaults to demo.docusign.net when DOCUSIGN_BASE_URL is
     unset (lib/esignature.ts:85) and posts to ".../v2.1/accounts/me/envelopes",
     where "me" is a placeholder for the real account id
     (lib/esignature.ts:90, repeated at :120 for status). No key is set anywhere.
     Shipping it means the first customer who clicks "send for signature" gets an
     opaque failure. The internal provider (1.4) is real and is enough for 1.0.0.
     How: render only 'internal' in the provider list; leave the adapter code.
3.3  Approval rules in the RBAC page — HIDE the tab.
     Why: task #21 measured that it has no storage to read; it is a UI with
     nothing behind it.
3.4  The 3 remaining dead fetch targets from task #22 — HIDE those panels.
     Why: a widget that always shows "—" reads as broken to a paying customer.
3.5  Data-retention ENFORCEMENT claims — HIDE the claim, keep the settings.
     Why: PP-046 closed the entity_type drift but enforcement itself is
     "still nothing but metadata". Any /legal/dpa or settings text implying
     automatic erasure must be softened or the feature enabled before GA.
3.6  Destructive cleanup jobs — DO NOT ENABLE without a decision.
     Why: task #54 flags that wave-2 routes are already on the live schedule,
     including cleanup (0 4 * * 0 in deploy/cron/crontab). purge_trash() covers
     4 of 6 trash tables (task #57). Confirm the schedule is what you want
     running unattended before you call the release stable.
3.7  lead-warming and process-lead-scoring — HIDE (unscheduled + unverified).
     Why: they are in the 5 routes that never fire (2.2) and have no live
     evidence. Shipping the UI for them invites "why is this doing nothing?".
3.8  Vercel cron config (vercel.json) — keep out of the 1.0.0 story.
     Why: deploy/cron/crontab's own header states the one-scheduler-per-
     environment policy (#1422); production is pm2 on a VM. Enabling both is the
     documented double-fire risk.
3.9  Selective restore from the panel — keep, but label internal/experimental.
     Why: PP-044 — its first write was rejected 42501, 3 tables hold 0 rows, and
     the policy escape is an open owner decision (task #90).
3.10 Claims 1.0.0 must NOT make, because nothing in the repo backs them:
     - an uptime SLA or support-hours commitment (no SLA document exists);
     - a public status page (only app/health API, no status site);
     - "monitored and alerted" (2.12 — alerts have never been delivered);
     - "automated offsite backups" until 2.4 produces one and 2.7 restores it;
     - "beta" anywhere inside the 1.0.0 scope (3.1 lists the strings to remove);
     - "PCI/SOC2/ISO" — there is no attestation file in the repo.
